## A. 음주 행동·정책·상태

### 구현할 것

- 기존 맥주·쌀술·과실주·벌꿀주·감로주·증류주 재고를 실제로 소비하는 여가 행동.
- 장수별 음주 허용/금지·간격 설정. 어린 캐릭터 음주 금지. 일반 장수는 소집 중 음주하러 이탈하지 않음.
- 일시적 기분 상승, 취기에 따른 능력 저하, 음주량/도수에 따른 취기 누적과 시간 경과 감소.
- 만취 시 행동 불가, 과음 후 숙취. 취기·숙취·금단을 구분해 표시.
- 알코올 의존 및 술에 약함/강함의 확정 동작. 의존 충동은 일반 음주 제한의 예외이며 소집·작업·금지 명령을 무시하고 술을 찾을 수 있음. 이름·이탈 이유 알림.
- 술을 찾기만 해서는 의존 충동·금단이 해소되지 않음. 실제 음주 후 소집 상태에 맞춰 전투/일반 행동으로 복귀.
- 정책·취기·숙취·의존 관련 진행 상태의 저장/복원 및 구저장 기본값.

### 재사용·주의

술 제조는 이미 있다. `Data/ProcessingResources.cs`, 생산 시설, `CommanderNeeds` 관련 생활·기분·작업 로직, 기존 특성/상태/저장 체계를 활용한다. `UI/GameMenuManagement.cs`의 음주 항목은 현재 미구현 안내다.

정확한 도수·간격·효과 수치·특성 등급·의존 발생 확률·치료/회복 방식은 확정 여부를 먼저 확인한다. 기획상 미정인 규칙을 임의 채택하지 않는다. 허용되는 잠정 수치는 값과 이유를 기록한다.

### 완료 기준

실제 재고 감소→음주→상태/기분 변화→시간 경과 회복을 확인한다. 어린이/금지/간격/소집 제한, 의존 예외, 술 없음, 중단, 저장/로드의 대표 경로를 검사한다. 실제 사용 가능한 정책 조작과 상태 표시가 있어야 한다.

## B. 식재료·가공품·요리 확장

### 먼저 품목 대조표 작성

자원 기획의 확정 목록을 `기획 품목 / 기존 ID·대체 표현 / 구현 여부 / 획득 경로 / 가공·소비 경로 / 연구 조건 / 남은 미정`으로 대조한다. 이미 있는 밀·보리·쌀·포도·해바라기, 제분·착유·양조·증류·훈연 및 기존 요리를 다시 만들지 않는다. 대체 표현이 기획을 충족하는지 확인한 뒤 실제 누락만 구현한다.

### 구현할 것

- 확정 목록에 있는 미구현 식재료와 작물: 곡물·채소·과일·견과·버섯·기호 작물 등. 예: 옥수수·호밀·메밀 및 관련 생산 경로.
- 가공품: 미구현 두부·두유, 버터·치즈·요구르트, 설탕·잼·절임·통조림, 식초·간장·된장 등 확정 목록.
- 요리: 죽·주먹밥·덮밥, 빵·면, 수프·채소·고기·수산·알·곤충 요리, 후식·음료 등 확정 레시피.
- 생산 주문→재료 예약·실물 배송→작업→바닥 배출→운반·보관→식단/섭취까지 연결.
- 품목별 부패·신선도·허용 대체 재료·필터·연구 해금·구저장 호환을 기존 규칙에 연결.

### 재사용·주의

현재 주방 레시피는 간단한 요리·좋은 요리·밥·납작빵·볶음밥·훈연식이다. `Buildings/Kitchen.cs`, `Kitchen.Food.cs`, `Data/ResourceType.cs`, `CookedFoods.cs`, `ProductionInputs`, 식단·식품 저장 체계를 재사용한다.

- 식재료 채택만으로 새 사육 동물 전체와 포획·번식 규칙이 승인된 것은 아니다. 공급 경로가 미정인 품목은 그 의존성만 보류한다. 무료 생성으로 메우지 않는다.
- 비용·산출량·시간은 기획에 확정된 값이 있으면 따르고, 미정 규칙과 조정 가능한 밸런스 수치를 구분한다.
- 반죽·썬 채소·국물처럼 기획에서 조리 과정으로 정한 것을 별도 재고 자원으로 만들지 않는다.
- 기존 자원 enum/저장 ID 순서를 바꾸지 않는다. 새 ID는 호환 가능한 방식으로 추가한다.

### 완료 기준

품목 대조표에 모든 확정 품목의 상태와 근거를 남긴다. 독립 구현 가능한 누락은 완료한다. 각 생산 사슬 유형을 실제 자원 획득부터 섭취까지 실행하고 재료 부족·중단/재개·부패·저장/로드를 확인한다. 기존 요리/생산 회귀 검사도 실행한다.

- 기존 보스 A 이후 탐지 장치 사슬과 보상 회수 규칙 유지.

### 현재 코드 근거

최초 단서 이벤트 조건, 통신 연구의 정확한 선행·비용·시대는 미정 여부를 확인한다. 시험용 단서 주입은 검사 도구에서만 사용하고 실제 획득 경로와 구분한다. 단서 획득→영구 공개→출정 대상 표시→저장/로드를 검사하고 기존 탐지 사슬을 회귀 검증한다. 디버그 공개만 되는 상태는 완료가 아니다.

## D. 도보와 차량 사이의 수송 단계

### 구현할 것

- 기존 도보·차량·항공에 손수레·동물 수레·마차 단계를 연결.
- 손수레는 실제 견인 인원이 필요하고 화물 용량을 확장.
- 동물 수레는 운송용 동물의 먹이·부상·이탈과 연결. 기존 사육·의료 상태 재사용.
- 이전 수단도 선택 가능하게 유지. 짧은 거리·소량 화물에 도보/수레 사용 가능.
- 각 수단의 편성·적재·이동·정원·수리·저장 일관성 확보.

### 경계·완료 기준

현재 `ExpeditionTransport`는 `Walking`과 `Aircraft`로 도보/차량/항공을 구분한다. 구저장 해석을 보존한다. 동물 종, 결합/해제, 마차 차별점, 통행 제한, 연구 배치가 미정이면 해당 부분만 분리한다. 없는 동물을 임의 추가하거나 수레를 차량 이름 변경으로 처리하지 않는다. 구현 가능한 각 수단에서 실제 편성·배송·이동·귀환·저장 검사를 수행한다.

## E. 본거지 외곽 길목 호위·복귀·원군

### 구현할 것

1. 원정 인원·화물과 호위 장수·병력을 별도로 편성한다.
2. 별도 전투 맵 대신 기존 본거지 로컬 맵 외곽 길목을 실제로 이동한다.
3. 원정대는 자동 이동하며 일시정지·재출발 가능. 호위대는 플레이어가 직접 지휘한다.
4. 실제 출발 경계 도착 후 원정대만 월드맵 이동으로 전환한다. 적 전멸을 출발 조건으로 삼지 않는다.
5. 호위대는 길목에 남아 전투하며 본진으로 복귀한다. 실제 도착 전에는 정착지 업무 복귀 처리하지 않는다.
6. 호위대 복귀 실패로 이미 출발한 원정을 취소하지 않는다.
7. 출정 호위전과 호위대 복귀전에 본진 원군을 요청하고 실제 이동 후 합류한다.
8. 외부 활동을 마친 원정대의 귀환에는 별도의 맞이 호위전을 추가하지 않는다.

### 재사용·주의

`ExpeditionTransport.TryDepart`는 현재 즉시 Outbound로 전환한다. 기존 원정 상태·승무원·화물·실물 이동·전투·저장 구조를 확장한다. 새 개별 병사·분대 시스템을 만들지 않는다. 시민 병력은 기존 수량/부대 체력 표현을 유지한다.

본진 잔류 의무, 동시 웨이브, 낙오/전멸/구출/화물 손실, 길목 재출현, 원군 제한·회수의 미정 규칙은 자동 확정하지 않는다. 길목 길이·입구 수·경로 봉쇄·차량 폭·스폰 간섭 역시 미정/검증 경계를 기록한다. 출발 차단 해제는 위 충돌과 필수 경계 처리가 정리된 뒤 별도로 명시한다.

### 완료 기준

실제 출정 준비→길목 자동 이동/직접 호위→경계 통과→원정대/호위대 분리→호위대 복귀→원정 귀환을 확인한다. 원군의 실제 이동·합류, 경계 중복 진입, 중간 저장/로드에서 인원·화물 복제/소실과 순간 출발이 없는지 검증한다. 길목 도착 전 Outbound 전환이 없어야 한다.

## 범위 제외

- 로켓 목적·승리 조건·최종 방어전 재설계.
- 웨이브 적 종류·편성·예고의 새 미정 규칙.
- 원정 중 웨이브와 본진 최소 잔류 규칙의 임의 확정.
- 새로운 세계관에 따른 시작 자원·시작 시설의 임의 교체.
- 그래픽·캐릭터·애니메이션 전면 작업, 전체 UI 재설계.
- 이번 지시와 무관한 리팩토링·기능 삭제.

## 검증과 결과 보고

- 공식 Unity CLI 컴파일, 변경 영역의 의미 있는 검사, 관련 기존 회귀, 격리 Play를 수행한다. 최종 통합 Player 빌드·실행은 점유를 조율해 수행하고 미실행이면 이유를 적는다.
- enum·직렬화·저장 버전 변경은 이전 저장 로드와 새 기능 진행 중 저장 왕복을 확인한다. 사용자 저장 슬롯을 시험에 사용하지 않는다.
- 기능별로 `완료 / 부분 구현 / 기획 결정 대기 / 미검증`을 구분한다. 시험용 데이터·디버그 진입만으로 성공한 결과는 실제 게임 연결 완료로 기록하지 않는다.
- 변경 파일, 플레이 변화, 실행한 검증과 결과, 잠정 수치, 남은 결정/충돌, 다음 담당 범위를 인계 문서에 남긴다. README에는 실제 구현된 현재 상태만 반영한다.
- 별도 SAVE 요청 전에는 SAVE·원격 push·Notion 기록을 수행하지 않는다. SAVE 요청 시 프로젝트 SAVE 절차를 따르며 `.prefab`과 `.prefab.meta`는 커밋하지 않는다.
